Operadores de pesquisa (referência)
intitle:
Restringe resultados com palavras-chave específicas no título.

inurl:
Filtra URLs que contenham uma string na path/query.
Ex.: inurl:admin
filetype:
Limita a ficheiros de um tipo (extensão).
Ex.: filetype:pdf
intext:
Procura texto no conteúdo indexado (corpo da página).
Ex.: intext:password
site:
Restringe a um site ou domínio.
Ex.: site:wikipedia.org
related:
Sites relacionados ao URL/domínio indicado.
Ex.: related:wikipedia.org
cache:
Versão em cache do Google para um URL (quando disponível).
Ex.: cache:wikipedia.org
"…"
Correspondência exata à frase entre aspas.
Ex.: "Wikipedia"
+
Termo obrigatório (sinónimo histórico; hoje o espaço já implica AND).
Ex.: jaguar +car
-
Exclui termo dos resultados.
Ex.: jaguar speed -car
OR
Combina alternativas (maiúsculas ajudam o Google a interpretar).
Ex.: jaguar OR car
imagesize:
Em pesquisa de imagens: filtra por dimensão.
Ex.: imagesize:320x320
@
Associado a handles em redes sociais (contexto Google).

#

$

PAINEL ESQUERDO — GUIA

O lado esquerdo é o cockpit do GhostRecon: define alvo, escopo, OPSEC, módulos, Vigolium, IA, relatórios e páginas auxiliares. Use este guia quando um campo parecer “mais uma caixa misteriosa”.

Topo e alvo

Projeto (pasta local)
Nome opcional do cliente/projeto. Quando preenchido, o run também grava corpus e SQLite em escopo/{projeto}/{dominio}/ghostrecon.db, além do storage configurado.
Target ($)
Alvo principal do recon. Aceita domínio, URL, IPv4 ou IPv6. Esse valor alimenta o pipeline, Reporte, Ghostmap, Workbench e filtros de alvo.
Fila de alvos
Roda vários alvos em sequência. O Target ($) é o primeiro; a textarea adiciona os próximos. É mais seguro para rate limit do que paralelizar tudo.
Fora de escopo
Lista hosts/URLs/wildcards que não devem entrar em corpus, sitemap, superfície HTML nem Google CSE. Também soma com GHOSTRECON_OUT_OF_SCOPE do servidor.

"Impressão digital adorável"

"Auditoria Supabase" / "Bypass pagamento"
supabase_audit é somente leitura. Requests anônimos aceitam apenas sb_publishable_* ou JWT legado exatamente role=anon; sb_secret_*, service_role, tokens authenticated/custom e chaves opacas inválidas falham antes da rede. Em <ref>.supabase.co, o ref do JWT anon deve coincidir. O Lovable usa o mesmo extrator fail-closed e só reporta credencial privilegiada estaticamente. GHOSTRECON_SUPABASE_AUTH_TOKEN aceita apenas JWT de usuário configurado, com issuer do projeto e exp futuro; sua assinatura não é atestada. Nenhuma conta, linha, arquivo ou RPC mutável é criado.
"Auditoria Firebase" / "RTDB/Firestore"
Leia como firebase_audit — extrai config e nomes de coleção observados no JS, testa somente leitura anônima em RTDB/Firestore e listagem de Storage. Esta capacidade não cria contas nem altera dados.
"Auth client-side" / "sessionStorage bypass"
Leia como client_auth_audit — analisa bundles JS em busca de senhas hardcoded, gates de auth via sessionStorage/localStorage, rotas de painel admin e dados sensíveis no browser.
"Client surface audit" / "DOM XSS sinks"
Leia como client_surface_audit — auditoria generalista de superfície browser: sinks XSS, postMessage, prototype pollution, JSONP, WebSocket, Service Worker, JWT em storage, SRI, CSRF em forms, CSP fraca, source maps, OIDC misconfig, tabnabbing e mixed content.
"CORS audit" / "Origin 500"
Leia como cors_audit — testa wildcard Access-Control-Allow-Origin: *, reflexão de Origin com credenciais, HTTP 500 em Origin desconhecida e preflight OPTIONS em /health, APIs e URLs do recon.
ALL
Visão geral da sessão (exclui dorks para reduzir ruído). Dorks ficam no separador DORKS.
🔴 HIGH
Apenas achados com prioridade alta (heurística de risco ou confirmações mais fortes).
🟡 MED
Prioridade média — candidatos a investigar sem ser o topo da fila.
🟢 LOW
Prioridade baixa — contexto, intel passiva ou ruído provável.
SUBS
Subdomínios com DNS (A/AAAA) que resolvem: crt.sh, VirusTotal, subfinder/amass (Kali), etc., fundidos no mesmo fluxo.
HOSTS
Subdomínios em que o subfinder (Kali) contribuiu para a descoberta; o texto do cartão inclui tool=subfinder no meta.
ENDPOINTS
URLs ou caminhos (Wayback, Common Crawl, sitemap/robots, superfície HTML, Google CSE, JS, etc.).
PARAMS
Nomes de parâmetros de query extraídos do corpus de URLs (e descoberta activa quando aplicável).
SECRETS
Padrões que parecem segredos (ficheiros JS, GitHub Code Search) — tratar como suspeitos até validares.
NMAP
Saída do nmap no modo Kali (serviços e versões na amostra analisada).
EXPLOIT.DB
Referências do searchsploit associadas a produto/versão detectados (modo Kali).
NUCLEI
Resultados do Nuclei (incluindo passagens com tags XSS/SQLi quando há candidatos no corpus).
WPSCAN
Enumeração WPScan (WordPress) só quando o recon passivo já indicou WordPress e a ferramenta existe no Kali. Por defeito exige WPSCAN_API_TOKEN (WPVulnDB); GHOSTRECON_WPSCAN_REQUIRE_API=0 permite scan só com enumeração. Os eventos na consola usam o prefixo [WPScan].
DALFOX
Resultados do Dalfox (XSS) no modo Kali, quando o pipeline activa essa fase.
XSS_VIBES
Executa duas requisições GET por parâmetro candidato com marcador não executável, redirect manual e escopo validado. Reflexão repetível gera apenas candidato; encoding correto vira inventário, nunca XSS confirmado.
XSS
Achados classificados como XSS (ex.: templates Nuclei ou fase Verify).
SQLI
Achados classificados como injecção SQL (Nuclei, Verify, etc.).
LFI
Inclusão local de ficheiros / path traversal levantados na verificação com evidência.
REDIRECT
Open redirect (fase Verify ou ferramentas que emitam esse tipo).
IDOR
Inseguranças de controlo de acesso / IDOR reportadas pelo pipeline de verificação.
